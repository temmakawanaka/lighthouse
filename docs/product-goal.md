# 灯台アプリ 完成条件

## 最終ゴール

スマートフォンで次に訪れる灯台を探し、歴史・諸元・参観条件を確かめ、公式情報や地図へ進んで訪問を判断できる、日本の灯台のフィールドガイド。

## 今回の完成範囲

- 既存の「のぼれる灯台16」をすべて収録し、詳細ページを直接開ける。
- 名前・かな・英語名・地域の検索、都道府県・参観可否の絞り込み、並び替え、ページングを維持する。
- URLで検索条件を復元し、詳細から条件付きの一覧に戻れる。
- 参観時間・料金・休止情報の根拠と確認日を示し、公式ページ・地図・電話へ進める。
- 不明な値と参観できない状態を区別し、架空の数値を補わない。
- API・DBの常時稼働を必要とせず、静的ファイルとして配信できる。従来のFastAPI接続も維持する。
- スマートフォン・キーボード操作・読み込み中・0件・404・APIエラーの既存品質を維持する。
- 自動テスト、型チェック、静的出力の検証を通し、変更をGitHub上でレビューできる。
- 16基を実写真で見比べ、地図から地域を選べる。
- 「行きたい」「訪問済み」を会員登録なしでこの端末に保存し、マイ灯台で振り返れる。
- ホーム画面へ追加でき、訪問済みページは再訪時にオフラインでも開ける。
- 公式参観ページの変更候補を毎日自動検知し、カタログを自動改変せずレビューへつなげる。
- 最大5基の訪問順と直線距離を整理し、Google Mapsのドライブルートへ進める。
- 端末の許可を得た時だけ現在地を使い、位置情報を保存・送信せず近い灯台を探せる。
- 訪問日と500文字までのメモを端末内に残せる。
- 行きたい・訪問済み・訪問メモ・旅程をJSONでバックアップし、別端末へ復元できる。
- 灯台と訪問順・予定日だけをURLで共有でき、受け取った側が確認してから保存できる。
- 一覧用と詳細用のWebP画像を使い分け、写真の通信量を抑える。

## 構成の判断

16基の公開情報の閲覧が中心で、更新は編集者が行うため、検索用データと詳細HTMLをビルド時に同梱する。閲覧機能・収録数・情報の精度は削らず、運用時の常駐サーバーとDBを不要にする。データ変更は再ビルド・再配信で反映する。

既存のNext.js／React／TypeScript、デザイン方針、FastAPI／PostgreSQLの実装は継続する。端末固有の記録はブラウザ内に保存し、共有URLへ訪問メモを含めない。

## 将来の拡張条件

- 会員間・端末間での訪問記録の同期や共有が必要になった時に、認証とサーバー永続化を追加する。
- 編集頻度や収録数が増え、ビルド時更新が運用上の支障となった時にAPI構成を再評価する。
- 全国の他の灯台への収録拡大は、出典を確認してから行う。

会員登録、投稿、決済は現在の目的には不要なため追加しない。有料リソースを前提とせず、静的配信を維持する。
